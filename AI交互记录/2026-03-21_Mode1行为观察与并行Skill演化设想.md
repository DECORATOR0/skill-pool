1. `router`
2. `executor`

- 再把候选 skill 压缩成更高阶、更稳定的 skill 库

## 先给总判断

### 1. 当前 `mode1` 的主行为不是“不会路由”，而是“已经基本会路由，但执行策略仍在收敛”

从 90 个 iteration 看，router 选择最频繁的 skill 为：

- `single-date-lst-threshold-proportion`: `30`
- `multi-date-raster-series-analysis`: `21`
- `<none>`: `8`
- `multi-date-lst-threshold-ratio-counting`: `7`
- `multi-year-split-window-lst-trend`: `6`

这说明：

- 冷启动期确实有 `no applicable skill`
- 但后期大量任务已经能落到稳定的 skill 家族
- 真正拖慢收敛的更多是 execution policy、tool contract、step budget、returned path 复用这些问题

### 2. 当前 skill 库已经出现“稳定小库”形态

最值得注意的不是 skill 数量，而是 skill 的写法已经明显从“功能名片”变成“执行规程”。

例如：

- `single-date-lst-threshold-proportion` 已经写出严格的 retrieval 分支表，明确何时用 `split_window`、何时用 `lst_single_channel`、何时用 `ttm_lst`、何时用 `temperature_emissivity_separation`
- `multi-date-raster-series-analysis` 已经写出很多硬约束：只调用一次 `get_filelist`、必须复用工具返回路径、不能拿 partial subset 提前聚合、先估算 step budget 再决定是否开跑
- `multi-year-split-window-lst-trend` 已经从“只会 emissivity + split_window”修到“有 emissivity 走 `split_window`，没有 emissivity 但有 BT31/BT32 时回退 `lst_multi_channel`”

所以这里的 `skill` 已经不是一个短标签，而是一份“受约束的程序性执行说明”。

### 3. 当前串行训练的强项是稳定修正，短板是探索速度太慢

`mode1` 已经证明串行训练能做到：

- 先建出第一批可复用 skill
- 再逐轮把 skill 细则写得越来越硬
- 最终让部分任务变成一次命中、一轮结束

但它的弱点也越来越明显：

- 新长尾任务要排队等前面的任务走完
- 同一个 skill 的长链路修正需要跨多个任务慢慢逼近
- 像 `task_39_39` 这类月尺度多日期任务，会反复消耗 iteration 在一个 skill 上做局部打磨

这正是并行候选 skill 生成值得考虑的地方。

## 五个角色分别在做什么

## 一、`router` 在做什么

### 角色定位

`router` 不是在“规划工具序列”，而是在“从当前 skill 库里选最像的一支”。

它的核心行为是：

- 读取当前 task prompt
- 看当前 skill headers
- 给每个 skill 打分
- 只有分数过阈值才选中
- 否则宁可返回 `no applicable skill`

### 行为特征

#### 1. 冷启动期：宁可不选，也不会乱选

代表例子：`task_02_2`

- iteration 1
  - router 返回 `selected_skill=""`
  - `has_applicable_skill=false`
  - 说明当前库里只有年度 TVDI 趋势 skill，不够覆盖单日期 TVDI 阈值题

这里 router 的行为其实是对的。问题不在 router 太弱，而在 skill 库太窄。

#### 2. 中期：会选到相近 skill 家族，但边界仍然粗

代表例子：`task_10_10`

- iteration 1
  - router 选中 `single-date-lst-threshold-proportion`
  - 但这道题真正要的是 NDVI 条件下的均温比较

这说明 router 已经能看出“这是单景、LST、统计题”，但对“阈值比例”和“条件均值比较”这种更细的任务意图还会混。

#### 3. 后期：skill 身份已稳定，问题更多转向 skill 内部策略

代表例子：

- `task_35_35`
  - router 直接命中 `single-date-lst-threshold-proportion`
  - 一轮完成
- `task_38_38`
  - 两轮都稳定命中 `multi-year-split-window-lst-trend`
  - 第一轮失败不是因为选错 skill，而是 skill 内部只会 emissivity 路径

所以后期 router 的主要价值不再是“创造新路径”，而是把任务稳定归到正确的 skill 家族上。

## 二、`skill` 在做什么

### 角色定位

当前框架里，`skill` 是 executor 的“受控作业规范”。

它至少承担四件事：

1. 定义触发边界
2. 约束允许调用的工具集合
3. 写清楚分支逻辑
4. 把过去失败经验沉淀成 guardrail

### 现阶段 skill 的真实形态

#### 1. skill 已经高度程序化

以 `single-date-lst-threshold-proportion` 为例，它已经明确写出：

- prompt 说 split-window 就必须用 `split_window`
- 不能把 emissivity 当 Red/NIR 乱代入 `lst_single_channel`
- 下游统计必须和问题问法一致
- raster-producing tool 的返回路径必须原样复用

这不是泛泛的“解题思路”，而是针对具体 runtime 的操作规程。

#### 2. skill 正在吸收失败经验，越来越像“修订过的 SOP”

以 `multi-date-raster-series-analysis` 为例，后期它已经吸收了很多失败：

- 不要反复 `get_filelist`
- 不要拿部分日期先聚合
- 先检查 step budget，再决定是否走逐日循环
- 不能猜测返回文件路径
- 若工具实际只支持 scalar，就不要沿用想当然的 batch 假设

这说明 skill 实际上在承担一部分“运行时风险约束层”。

#### 3. skill 也会被压缩

代表例子：`task_10_10` iteration 2

- actor 做了 `merge_skills`
- 目标 skill：`multi-date-raster-series-counting`
- 来源 skill：
  - `multi-date-lst-threshold-ratio-counting`
  - `multi-date-tvdi-spike-counting`

这说明框架里已经自然出现了“技能压缩”雏形，只是现在还很局部、很人工。

## 三、`executor` 在做什么

### 角色定位

`executor` 不是自由推理，而是在 skill 给定的边界里把任务真正跑起来。

它的主要工作是：

- 读 skill 说明
- 读 task prompt
- 选择具体工具
- 组织参数
- 执行工具链
- 给出最后答案

### 行为特征

#### 1. skill 对了时，executor 可以非常直接

代表例子：`task_35_35`

- router 选中 `single-date-lst-threshold-proportion`
- executor 轨迹：
  - `get_filelist`
  - `split_window`
  - `calculate_threshold_ratio`
- 一轮成功

这就是当前框架最理想的状态：

- 正确 skill
- 短工具链
- 无 critic / actor 介入

#### 2. 新 skill 一旦补上，executor 立刻能复用

代表例子：`task_02_2`

- iteration 1 还因为无 skill 而跳过
- actor 创建 `single-date-tvdi-threshold-analysis`
- iteration 2 executor 立刻执行：
  - `get_filelist`
  - `compute_tvdi`
  - `calculate_threshold_ratio`
- 成功得到 `28.07%`

这说明 skill 库的收益是立竿见影的，不需要额外训练 executor 参数本身。

#### 3. 当前 executor 的主要失败点不是“完全不会做”，而是“执行得不够硬”

代表例子：`task_20_20`

- 4 个 iteration 都稳定使用 `multi-date-raster-series-analysis`
- 工具轨迹大致对：
  - `band_ratio`
  - `calc_batch_image_mean`
  - `count_spikes_from_values`
- 但最终结果始终没压到正确答案

这类失败更像：

- 场景覆盖不完整
- 路径复用不够严格
- 聚合输入不完整
- partial result 被过早拿去回答

#### 4. 长时间序列任务暴露出 step budget 问题

代表例子：`task_39_39`

- iteration 1 已经稳定选中 `multi-date-raster-series-analysis`
- executor 连续做了很多次 `modis_day_night_lst`
- 但在 20-step 上限内没能完成整个月的 daily LST 和最终计数

这类任务说明一个现实问题：

- skill 对
- 工具也对
- 但串行 executor 在长序列任务上会被 step budget 卡死

这也是并行/批处理化最值得下手的地方。

## 四、`critic` 在做什么

### 角色定位

`critic` 的职责不是“重做一遍任务”，而是：

- 根据本轮执行结果
- 对照 gold 轨迹与评价信息
- 判断这是 coverage gap、skill 边界问题，还是 execution policy 问题
- 再给 actor 一个动作建议

### 行为特征

#### 1. critic 在冷启动期负责指出“该建什么 skill”

代表例子：`task_02_2`

critic 判断：

- 任务本来可解
- 之所以失败，是因为当前库缺少“单日期 TVDI 阈值分析” skill
- 所以推荐 `create_skill`

这一步非常关键，因为它把“失败”变成了“能力缺口定义”。

#### 2. critic 在中后期更像 skill 代码审查员

代表例子：`task_20_20`

连续四轮 critic 都推荐 `modify_skill`，核心不是说“skill 家族错了”，而是：

- 应该强制全序列处理
- 应该精确复用工具返回路径
- 应该避免 incomplete batch aggregation

所以中后期 critic 主要在做 execution policy 级别的精修建议。

#### 3. critic 已经能识别“假 blocker”

代表例子：`task_38_38`

critic 明确指出：

- router 选对了
- 错不在任务族
- 而在 skill 把 emissivity 缺失当成绝对 blocker
- 实际应当回退 `lst_multi_channel`

这说明 critic 已经能把“路由问题”和“工具前提误判”分开。

#### 4. critic 也会对 step-budget 型问题给出结构性信号

经验库最新两条关于 `task_39_39` 的记录都在强调：

- executor 串行逐日跑太慢
- 没进入最终 `count_images_exceeding_threshold_ratio`
- duplicate-date 处理还在漂移

这类 critic 信号已经不是局部 bug，而是对训练框架本身的提醒。

## 五、`actor` 在做什么

### 角色定位

`actor` 负责把 critic 的判断真正写回系统。

它的动作类型目前主要有三种：

1. `create_skill`
2. `modify_skill`
3. `merge_skills`

### 行为特征

#### 1. 前期 actor 主要负责补族

代表例子：`task_02_2`

- actor 创建 `single-date-tvdi-threshold-analysis`

代表例子：`task_10_10`

- actor 创建 `single-date-ndvi-conditioned-lst-comparison`

这说明 actor 早期主要在补“还不存在的任务家族”。

#### 2. 中后期 actor 大部分时间都在原地修 skill

从全局计数看：

- `modify_skill = 57`
- 远高于 `create_skill = 9`

这表示后期训练的主体已经变成“把 skill 写硬”，而不是继续扩库。

#### 3. actor 偶尔会做压缩

`merge_skills = 3`

虽然次数不多，但这非常重要，因为它意味着当前框架不是完全没有“skill 抽象上收”的能力，只是现在还停留在局部启发式层面。

#### 4. actor 会把经验写回 experience buffer

当前经验库最后几条，已经明显是结构化失败签名，而不是一句空泛总结。

例如：

- `task_38_38` 记录了“false blocker on multi-year BT31/BT32 LST task because skill required emissivity-only split_window and lacked lst_multi_channel fallback”
- `task_39_39` 记录了“月尺度 MODIS day/night 任务因为串行 per-date 执行和 duplicate-date 漂移而卡死”

这意味着 actor 不只是在写 skill，也在给未来压缩和聚类准备语义标签。

## 对“并行产 200+ skill，再压缩”的看法

## 一、这个想法是成立的，而且和当前观测是吻合的

当前 `mode1` 最慢的地方正是：

- 新 skill 家族发现速度慢
- 长链路 task 用很多 iteration 去微修同一 skill
- 许多 failure signature 明明已经很像，却还要在不同 task 里重复出现后才能沉淀

所以，把训练拆成：

1. 并行候选生成
2. 候选归并压缩
3. 再回灌主库

是有明显合理性的。

## 二、但我不建议“只靠文本聚类后让大模型总结”

纯文本聚类不够，原因是当前 skill 不是纯语义对象，而是带有强 runtime 约束：

- tool family
- allowed-tools
- 输入输出契约
- returned-path 复用规则
- step budget 敏感性
- 批处理与 scalar 兼容性

如果只看 skill 文本，很容易把语义相近但 runtime 契约冲突的 skill 错并。

更稳的做法应该是“结构化压缩”，而不是“只看 embedding 压缩”。

## 三、我更建议的方案：三层 skill 体系

### 第 1 层：候选 micro-skill

来源：

- 每个任务独立并行跑
- 每题最多 4 个 iteration
- 不共享主 skill 库写权限
- 每个任务只产出自己的局部 skill 候选和失败签名

这里的目标不是立刻进主库，而是尽量多探索。

### 第 2 层：cluster / graph 级 meso-skill

对所有候选 skill 做结构化归并，至少使用这些特征：

- task family embedding
- tool multiset / tool sequence signature
- input contract signature
- output contract signature
- failure signature
- 是否依赖 step budget
- 是否依赖 returned-path reuse
- 是否依赖 batch/scalar tool schema

这里不只是聚类，也可以做图合并：

- skill 与 task 形成二部图
- skill 与 tool contract 形成约束边
- 相同失败模式形成修正边

### 第 3 层：主库 canonical skill

对每个 cluster 让大模型做一次“总结式升维”，但必须附带验证：

1. 先生成候选高阶 skill
2. 再拿该 cluster 的 held-out task 做回放
3. 通过后才升入主库
4. 未通过则回退到 meso-skill 或继续拆分

这样做的好处是：

- 不会让主库被大量脏 skill 污染
- skill 压缩不再只是文本摘要
- 压缩后的 skill 依然有行为验收

## 四、推荐的并行训练流水线

### 阶段 1：候选生成

- 每个 task 独立 worker
- 每个 worker 有临时 skill 库和临时 experience buffer
- `max_iterations_per_task = 4`
- 产出：
  - task 级 skill 候选
  - critic/actor 决策
  - failure signature
  - 成功率、步数、工具轨迹

### 阶段 2：标准化

把每个候选 skill 转成统一记录：

- `skill_name`
- `description`
- `allowed_tools`
- `consumption_mode`
- `tool_sequence_signature`
- `input_contract_signature`
- `output_contract_signature`
- `failure_signatures`
- `supported_task_examples`
- `unsupported_task_examples`
- `mean_success_rate`
- `mean_step_count`

### 阶段 3：候选去重与聚类

建议先做粗分桶，再做精聚类：

1. 先按 `consumption_mode` 分开
2. 再按主工具族分开
3. 再按任务描述 embedding 和 failure signature embedding 聚类
4. 对 cluster 内文本近似但 contract 冲突的 skill 再做拆分

### 阶段 4：LLM 升维总结

对每个 cluster 让大模型生成更高阶 skill，但要强制输出：

- 适用边界
- 不适用边界
- 必须复用的工具契约
- 常见失败与 guardrail
- 最小正确执行模板

### 阶段 5：tournament 验证

不是直接替换主库，而是做对打：

- 原 cluster 内各 skill
- 新生成的高阶 skill
- 在 held-out task 上比较
  - 成功率
  - 平均步数
  - tool contract 错误率
  - returned-path 错误率

只有胜出的版本才进入主库。

### 阶段 6：主库晋升与回灌

把通过验证的高阶 skill 写入主库，同时保留：

- 来源候选 skill 列表
- 压缩理由
- 失效风险
- 可回退版本

这样后面 debug 时还能追溯“这个高阶 skill 是从哪些 micro-skill 抽上来的”。

## 五、对 `mode1` 和 `mode2` 的差异化建议

### `mode1`

压缩时更应该看：

- 工具链形态
- 输入输出契约
- returned-path 复用规则
- aggregation 规则
- step budget 风险

因为 `mode1` 的核心是 executor-style procedural skill。

### `mode2`

压缩时不能只看 executor skill，还要单独看 planner-style skill：

- plan skeleton 是否稳定
- parameter binding 是否稳定
- planner worker 是否经常超时
- answer selector 是否引入额外漂移

也就是说，`mode2` 的高阶 skill 可能不是“执行模板”，而是：

- 规划模板
- 参数绑定模板
- planner-runtime fallback 模板

因此两边不能完全用同一套聚类特征。

## 六、为什么这个方案比继续纯串行更有吸引力

我认为并行方案的真实价值不只是“更快”，而是把两种本来混在一起的学习过程拆开：

### 当前串行里混在一起的两件事

1. 探索新 skill 家族
2. 打磨已有 skill 执行细节

一旦拆开，系统会更清楚：

- 哪些 task 只是需要已有 skill 的 patch
- 哪些 task 真的需要新 skill
- 哪些 skill 其实只是现有 skill 的变体，应该被压缩

## 七、我建议的最小实验版本

如果要低风险试这个思路，我建议先不要直接上“全量并行 + 200+ skill”。

先做一个小版本：

1. 选 20 个 task
2. 每题独立并行，最多 4 iteration
3. 临时 skill 库互不共享
4. 收集所有候选 skill 与 failure signature
5. 做一次离线聚类 + LLM 总结
6. 拿压缩后的 skill 库跑 held-out eval

如果这一步能证明：

- 覆盖率上升
- 技能数没爆炸
- 聚合后的 skill 不比原始 skill 差

再扩大到全量。

## 八、相关资料与支撑

下面这些资料支持的是“方向”与“构件”，不是说它们直接给出当前项目的最终实现。

### 1. Voyager：证明“不断积累并复用 skill 库”是可行的

- Voyager 强调 ever-growing skill library、环境反馈迭代修正和新任务复用
- 对我们最有启发的是“先形成可执行 skill，再跨任务复用”
- 链接：https://arxiv.org/abs/2305.16291

### 2. SkillRL：支持“从 raw experience 蒸馏出层级化 SkillBank”

- SkillRL 明确提出 experience-based distillation、hierarchical SkillBank、recursive evolution
- 这和“先并行产候选，再向上压缩”为高阶 skill 库”最接近
- 链接：https://arxiv.org/abs/2602.08234

### 3. SkillVerse：支持树状/层级化能力组织，而不是纯平铺技能表

- SkillVerse 用 dendrogram 组织能力层次
- 对我们最有启发的是 skill 不一定只能平铺管理，也可以树状归并
- 链接：https://arxiv.org/abs/2506.00319

### 4. A-MEM：支持把经验做成结构化记忆，而不是只保留原始轨迹

- A-MEM 强调结构化长期记忆组织
- 对我们对应的是：experience buffer 不应只是 append-only 文本，而应成为可聚类、可压缩的结构化输入
- 链接：https://arxiv.org/abs/2502.12110

### 5. Option-Critic：经典的层级 skill / option 理论支撑

- 它不是 LLM agent 论文，但提供了 temporal abstraction 的经典视角
- 能支撑“高阶 skill 本质上是 temporally extended policy”这件事
- 链接：https://arxiv.org/abs/1609.05140

### 6. DIAYN：支持先发现多样技能，再决定如何复用/压缩

- DIAYN 提供的是“先做 diversity-driven skill discovery”的经典思路
- 对应到这里，就是可以先接受一定的 skill 冗余，再在后处理阶段压缩
- 链接：https://arxiv.org/abs/1802.06070

## 我的结论

### 1. 当前 `mode1` 已经足够说明 skill 学习是有效的

证据不是成功率本身，而是：

- 已形成稳定小 skill 库
- 新 task 可以被已有 skill 一轮解决
- 大量失败已经从“完全不会”转成“skill policy 仍需微修”

### 2. 你提的并行方案值得做，而且很可能比继续纯串行更像下一个阶段

但我不建议直接做：

- “全量并行 -> 文本聚类 -> 大模型总结”

我更建议做：

- “并行候选生成 -> 结构化标准化 -> 聚类/图归并 -> LLM 升维 -> held-out 验证 -> 主库晋升”

### 3. 当前最像瓶颈的，不是 model 本身，而是 skill 生命周期管理方式

`mode1` 已经进入一个阶段：

- skill 增长不再是主问题
- skill 的整理、压缩、升维、验证，反而更重要

所以从工程上讲，下一阶段更值得投入的不是继续堆 iteration，而是做：

- 并行候选生产
- 结构化经验表示
- 高阶 skill 压缩与验收
