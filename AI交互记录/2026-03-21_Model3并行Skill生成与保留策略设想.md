# 2026-03-21 Model3并行Skill生成与保留策略设想

## 本轮讨论要点

- 继续保留当前 `mode2` 那套“又臭又长”的 prompt，不直接替换。
- 原因不是它优雅，而是当前正确率表现还可以，直接覆盖会把已有可用链路一起动掉。
- 另开一套新的 prompt / mode，专门生成更接近参考优良 skill 库风格的紧凑型 planner skill。
- 新 skill 结构优先参考：
  - `项目文档/参考技能库/协作者优良skill库`
- 这些参考 skill 的共同特征是：
  - 字段和章节更统一
  - 篇幅相对可控
  - 更像“分发给不同智能体的规划先验”，而不是不断累积的超长菜谱
  - 即使长短有差异，最长也没有膨胀到当前 mode2 某些 skill 的程度

## 对参考优良Skill结构的判断

当前更合理的方向不是继续在原 prompt 上无限叠加约束，而是直接承认两类目标并分流：

1. 现有 `mode2`

   - 保留，作为“当前效果还不错的长 skill 方案”
   - 不打断已有实验链路
2. 新的 `model three`

   - 单独设计
   - skill 结构向参考优良 skill 库靠拢
   - 更强调统一字段、清晰规划先验、便于后续并行生成与压缩

对新结构的判断：

- `SKILL.md` 应继续是主文件
- `references/REFERENCE.md` 不必强制存在
- 只有当以下信息明显会挤占主 skill 时，再放到 `references/`：
  - 较长的边界情况说明
  - 多个典型 family 的补充案例
  - 不适合塞进主 skill 的参数示例或长说明

也就是说，`reference` 在新模式里应是“可选扩展层”，不是默认堆料区。

## Model3 的初步定义

用户提出的新方向可以整理成下面这个范式：

- `model three` 不再像当前训练那样按任务串行慢慢演化
- 对每个子任务，直接并行跑一套原来的流程
- 每个子任务都尝试自己产出一个 skill
- 有多少个子任务，就可能产生多少个候选 skill
- 每个子任务内部的迭代上限提高到 `10`
- 如果某个子任务在中途已经成功，则提前停止
- 如果到第 `10` 次仍未成功，再停止该子任务

这个范式的核心价值不是让 prompt 自己在迭代过程中永远保持克制，而是：

- 先允许局部任务各自收敛
- 最后再对大量候选 skill 做统一筛选、归并、压缩

也就是把“篇幅控制”和“抽象压缩”从单任务在线迭代阶段，后移到并行产物的离线汇总阶段。

## 关键问题：跑满10次仍失败的Skill要不要保留

我的结论是：

- 不建议直接保留到正式 skill 库
- 更合适的是“正式库不保留，候选池可保留元信息”

### 为什么不建议直接进正式库

如果一个子任务在最多 `10` 次迭代后仍然失败，通常说明至少存在下面一种情况：

- skill 抽象方向本身就不对
- 路由到的工具族不对
- 规划模式不稳定
- 参数生成链路不稳定
- 该 skill 对成功帮助有限，甚至会带来错误先验

这类 skill 如果直接入正式库，会有几个明显问题：

1. 污染后续路由

   - router 或 planner 后面可能再次命中它
   - 命中后会把失败经验重新当成先验注入
2. 稀释好 skill

   - 并行模式下 skill 数量会很快变多
   - 如果失败 skill 也进入正式库，后续归并和筛选成本会明显上升
3. 失败并不一定意味着“完全没信息”，但往往不适合原样复用

   - 它更适合作为失败模式样本，而不是成品 skill

### 更合理的处理方式

建议把产物分成三层：

1. 正式库

   - 只放成功 skill，或至少放“达到明确成功阈值”的 skill
2. 候选池 / 隔离区

   - 存放跑满 `10` 次仍失败的 skill 草稿
   - 但不注入后续在线推理
   - 只保留给后续聚类、复盘、抽象总结使用
3. 经验缓冲 / 失败模式池

   - 记录失败签名、错误族、常见错用工具、错误顺序
   - 这些信息可以反哺新 skill 的合并与抽象
   - 但不直接作为 `SKILL.md` 被消费

## 我更推荐的保留策略

如果要一句话定策略，我建议：

- 成功 skill 进正式库
- 失败 skill 不进正式库
- 失败 skill 的“结构化痕迹”进入候选池或失败模式池

也就是：

- 保留“信息”
- 不保留“成品资格”

这是我目前最推荐的折中方案。

## 为什么不能简单全删

用户担心的是：

- 如果完全不保留，会不会丢掉一些其实接近成功、只是运气差一点的 skill

这个担心是合理的，所以我不建议“彻底物理删除”。

更合适的做法是：

- 不让它进入正式在线 skill 库
- 但保留其摘要、失败轨迹、最终版本、critic 反馈、工具调用统计

这样后面可以做两类再利用：

1. 聚类后抽象

   - 多个失败 skill 如果都卡在同一种 family 边界
   - 说明这里可能缺一个更高层、更稳的抽象 skill
2. 与成功 skill 对照

   - 看成功 skill 和失败 skill 差别到底在：
     - 工具选择
     - 顺序
     - 参数策略
     - stop condition
     - family 边界

所以失败 skill 最好是“不晋升，但不白丢”。

## 对Model3更完整的建议

基于本轮讨论，我认为 `model three` 可以按下面的思路设计：

### 1. Prompt层

- 保留现有 `mode2` prompt，不覆盖
- 新开一套 prompt
- 新 prompt 生成的 skill 结构向参考优良 skill 库靠拢
- `reference` 改成按需附加，而不是默认膨胀

### 2. 训练层

- 每个子任务并行独立迭代
- 单子任务最多 `10` 轮
- 中途成功立即停止
- 失败则在第 `10` 轮停止

### 3. Skill产物层

- 成功 skill：进入正式库
- 失败 skill：进入候选池 / 隔离区，不进正式库
- 失败模式：沉淀到经验池，供后续聚类和总结

### 4. 压缩层

- 后续再把大量 skill 做聚类
- 让大模型基于聚类簇总结出少量高质量高层 skill
- 这一阶段才是真正控制篇幅和提升抽象度的主战场

## 当前阶段的建议动作顺序

我认为后续实现顺序应为：

1. 保留现有 `mode2` 及其 prompt
2. 新开一套参考优良 skill 结构的 prompt 变体
3. 单独开 `model three`
4. 明确正式库 / 候选池 / 失败模式池三层机制
5. 再进入并行生成与后续压缩阶段

## 本轮明确结论

本轮最重要的结论有三个：

1. 当前长 prompt 先保留，不直接替换
2. 新结构应参考 `协作者优良skill库` 的统一字段风格
3. `model three` 中跑满 `10` 次仍失败的 skill，不应直接保留到正式库；更合理的是保留为候选或失败模式材料，供后续聚类和抽象
