# 项目架构与工作流说明书

这份说明书只做一件事：把这个项目现在的三阶段工作流讲清楚。

- 训练阶段
- 测试阶段
- 评估阶段

这里不再放 AI 工作约定、目录入口、问题清单、扩展代码说明。那些内容分别在 `给AI先看`、`待办` 和 `实验记录` 里维护。

## 1. 训练阶段

训练阶段对应的是：系统不仅做题，还会根据结果修改 skill 库。

### 1.1 训练阶段在做什么

一轮完整训练里，每道题都会经历这条链：

1. 读取当前 skill 库
2. router 给已有 skill 打分并选一个最合适的
3. executor 按选中的 skill 跑工具
4. environment 对结果做评测
5. 如果当前题已经成功，这题结束，不再调用 critic
6. 如果当前题没成功，critic 基于执行结果给出 reward 和修改建议
7. actor 决定：
   - `create_skill`
   - `modify_skill`
   - `merge_skills`
8. actor 把 skill 写回 skill 库
9. 进入下一轮 iteration，直到成功或者达到每题最大轮数

所以训练阶段的本质不是“单次求解”，而是“求解 + 学 skill”。

### 1.2 训练阶段最关键的参数

训练阶段最需要盯的是配置里的 `runtime`：

- `max_iterations_per_task`

  - 每题最多允许试多少轮
  - 值越大，skill 有更多机会被修改后重试
  - 值越小，训练更像一次性试跑
- `max_executor_steps`

  - executor 单题最多能走多少步
  - 遥感长轨迹题很容易被这个参数卡死
  - 对小模型来说，太大又容易把上下文堆爆
- `skill_match_threshold`

  - router 认定“这个 skill 足够适合当前题”的阈值
  - 高了更容易无 skill
  - 低了更容易错用旧 skill
- `skill_count_limit`

  - skill 库允许长到多大
  - 对训练后期很重要，直接影响 skill 是继续拆分还是开始压缩
- `max_actor_steps`

  - actor 侧的预算
  - 当前不是第一瓶颈，但 skill 写得越来越长时也会拖慢单轮训练

### 1.3 训练阶段常用的任务选择参数

- `--task-ids`

  - 明确指定训练哪些题
  - 适合做小范围定向实验
- `--count`

  - 从当前起点开始取前 N 题
- `--start-index`

  - 从数据集第几题开始取
- `--run-name`

  - 指定本次 run 名称
- `--reset-skill-library`

  - 从空 skill 库起跑
- `--reset-experience-buffer`

  - 清空经验库后再跑

### 1.4 训练阶段最典型的几种用法

#### 1.4.1 从空 skill 库开始跑一批题

适用于：

- 想看 skill 是怎么从 0 长出来的
- 想测 create_skill 的效果

重点参数：

- `--reset-skill-library`
- `--reset-experience-buffer`
- `--count` / `--task-ids`

#### 1.4.2 保留当前 skill 库，继续往后训练

适用于：

- 已经有一套初始 skill，想继续让后续题推动它演化

重点参数：

- 不要加 `--reset-skill-library`
- 只调整 `--count` / `--start-index` / `--task-ids`

#### 1.4.3 单题细查

适用于：

- 想看某一题为什么一直失败
- 想看 actor / critic / executor 在这题里具体怎么动

这时通常不是 `train-tasks`，而是 `debug-single-task`。

### 1.5 训练阶段的主要产物

训练 run 下常见文件：

- `config_snapshot.json`
- `selected_tasks.json`
- `task_01_x/`, `task_02_x/` ...

每个 task 下重点看：

- `task_summary.json`
- `iteration_01/`, `iteration_02/` ...

每个 iteration 下重点看：

- `skill_headers_before.json`
- `env/`
- `critic/`（仅失败 iteration 会有）
- `actor/`（仅失败 iteration 会有）
- `iteration_summary.json`
- `iteration_failure.json`

### 1.6 训练阶段应该怎么读结果

如果你是想判断一题为什么没过，优先看：

1. `task_summary.json`
2. `iteration_summary.json`
3. `env/executor/executor_steps/`

如果你是想判断 skill 是怎么演化出来的，优先看：

1. `critic/reward.json`（仅失败 iteration）
2. `actor/actor_decision.json`（仅失败 iteration）
3. `skill_headers_before.json` 和 `skill_headers_after.json`

## 2. 测试阶段

这里说的“测试”，是指仍然走训练链条，但把每题控制成很短的一次性试跑，用来观察当前系统行为，而不是深度演化 skill。

### 2.1 测试阶段在做什么

测试阶段本质上还是训练环：

- 还是会 router 选 skill
- 还是会 executor 执行
- 还是会 critic 评价
- 还是可能 actor 改 skill

但它强调的是：

- 每题只跑很少轮
- 更关注当前链条有没有跑通
- 更像“受限训练测试”

### 2.2 测试阶段最关键的参数

测试阶段最关键的是：

- `max_iterations_per_task = 1`
  - 这是最重要的开关
  - 一旦设成 `1`，每题只会试一轮

配合一起看的通常还有：

- `max_executor_steps`

  - 控制单题能走多远
- `--task-ids`

  - 定向测某几题
- `--count`

  - 做小批量测试

### 2.3 什么时候应该用测试阶段

适用于：

- 想保留当前 skill 库
- 想看 router / executor / critic / actor 整条链是否稳定
- 但不想让单题反复迭代 3 轮、4 轮、10 轮

尤其适合：

- 调试小模型稳定性
- 看当前 prompt / skill 是否会出现明显死循环
- 看 executor 在一轮里会不会直接炸 TPM、JSON、路径或工具契约

### 2.4 测试阶段和训练阶段的区别

它们的代码路径几乎一样，差别主要不在命令名，而在参数设置：

- 训练阶段：允许同题多轮迭代，强调 skill 演化
- 测试阶段：把 `max_iterations_per_task` 压成 `1`，强调当前链路行为

所以测试阶段更像：

- “训练流程的短跑版”

而不是：

- “完全不改 skill 的纯评估版”

## 3. 评估阶段

评估阶段对应的是：只评估当前 skill 库，不再改 skill。

### 3.1 评估阶段在做什么

每道题只做一次：

1. 读取当前 skill 库
2. router 选 skill
3. 如果命中 skill，就按该 skill 约束 executor 执行
4. 如果没有任何 skill 过阈值，评估阶段会触发一次无 skill 的 executor 保底执行
5. environment 输出评测结果
6. 写评估摘要

到这里就结束，不再调用 critic / actor 改 skill。也就是说，评估阶段只有 router、executor 和当前 skill 池参与。

### 3.2 评估阶段最关键的参数

评估阶段最常用的是：

- `--task-ids`

  - 精确评估哪些题
- `--count`

  - 从起点开始评估前 N 题
- `--start-index`

  - 控制评估起点
- `--run-name`

  - 给本次评估命名
- `skill_match_threshold`

  - 决定 router 何时算“命中 skill”
  - 如果没有任何 skill 过阈值，评估阶段就会进入无 skill fallback，而不是直接放弃作答

### 3.3 评估阶段会输出什么

每个 task 下常见：

- `evaluation_summary.json`
- `evaluation_failure.json`（如果中途崩）

其中 `evaluation_summary.json` 现在还会额外记录：

- `used_fallback_executor`
  - 这一题是否因为 router 没命中 skill 而走了兜底执行

run 根目录会汇总出：

- `evaluation_summary.json`

run 级汇总里会额外有：

- `fallback_count`
  - 本次评估一共多少题走了无 skill fallback

### 3.4 当前评估阶段看的指标

现在这套框架主要看：

- `accuracy`
- `efficiency`
- `tool_any_order`
- `tool_in_order`
- `tool_exact_match`
- `parameter_accuracy`

### 3.5 什么时候应该用评估阶段

适用于：

- 当前 skill 库已经形成一版
- 不想再让 actor 改东西
- 只想看这套 skill 库本身的推理效果

最典型的问题是：

- 这套 skill 库现在到底能过多少题
- 训练完之后到底有没有提升
- 哪一类题已经稳定了，哪一类题还没稳定

## 4. 三阶段怎么选

可以直接按目的选：

- 想让系统边做题边长 skill：用训练阶段
- 想看完整链条，但不想让单题反复迭代：用测试阶段
- 想冻结当前 skill 库，只看实际效果：用评估阶段

也可以按常见实验顺序理解：

1. 先训练，长出一版 skill
2. 再测试，确认当前链条短跑稳定
3. 最后评估，测这版 skill 库的真实效果

## 5. 这份说明书怎么用

后面你如果再看某个实验，只要先明确它属于哪一类：

- 训练
- 测试
- 评估

然后再看对应的核心参数：

- 训练：重点看 `max_iterations_per_task`
- 测试：重点看 `max_iterations_per_task = 1`
- 评估：重点看任务选择参数，不看 actor 修改

这样基本就不会把三种 run 混在一起理解。
