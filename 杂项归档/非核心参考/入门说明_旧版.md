# Project Skills 实验说明（极简版）

这份文档只回答 3 件事：

1. 每个任务的完整闭环在干什么
2. 常见参数加上后分别是什么意思
3. 平时怎么跑、跑完看什么、哪些结果要留

## 0. 先说结论

这个实验本质上是在做一件事：

> 用 benchmark 题目反复逼着系统选 skill、执行 skill、评估结果、再改 skill，直到 skill 库越来越能解题。

你可以把它理解成一个“会自己改操作手册的 agent 系统”：

- `skill_library/`：当前会用的方法库
- `runs/`：每次实验的完整轨迹
- `runtime_state/experience_buffer.jsonl`：跨任务累积的失败经验

注意：命令要在这个目录下运行：

```powershell
cd D:\skills-evo\project_skills\project_skills
```

不是仓库最外层。

## 1. 每个任务的完整闭环

### 1.1 训练模式：`debug-single-task` / `train-tasks`

对每个任务，系统会按下面这条链路跑：

1. 读取一个任务

   - 来自 `data/converted/earth_bench_skill_rl/question.json`
   - 里面已经有：题目、选项、数据目录、gold answer、gold tool trajectory、gold tool names
   - 这里的 gold 信息后面会被 `evaluation` 用来做硬对比
2. 扫描当前 skill 库

   - 只先读每个 skill 的头信息，不把整个 `SKILL.md` 全部塞进去
   - 这些头信息会先保存到 `skill_headers_before.json`
   - 这里记录的是“这一轮开始前系统手上有哪些 skill 可选”
3. `router` 选 skill

   - 输入：题目 + 现有 skill headers
   - 输出：选哪个 skill、每个 skill 打多少分、有没有达到路由阈值
   - 这个阈值是 `skill_match_threshold`
   - 注意：这个阈值只决定“要不要用这个 skill”，不决定任务成功
   - 如果没有 skill 过阈值，这一轮会进入“当前库里没有合适 skill”的分支
4. `executor` 执行 skill

   - 只有被选中的 skill 才会加载完整 `SKILL.md`
   - 然后按 skill 里的说明去调工具
   - 每一步工具调用、参数、返回值，都会被记录进执行轨迹
   - 例如一个“年度干旱趋势”题，理想工具链是：
     `get_filelist -> compute_tvdi -> calculate_tif_average -> calc_batch_image_mean -> compute_linear_trend`
   - 如果 router 没选出 skill，这一步不会真的执行工具，而是直接记成“无合适 skill”
5. `evaluation` 打分

   - 这是硬规则打分，不是 LLM 主观判断
   - 它会把这次执行结果和 gold answer / gold trajectory 直接对比
   - 关键指标包括：
     - `accuracy`：最终答案是否对
     - `tool_any_order`：该用的工具有没有用到
     - `tool_in_order`：顺序大体对不对
     - `tool_exact_match`：前缀是否精确一致
     - `parameter_accuracy`：参数是否和 gold 一致
     - `efficiency`：用了多少步，相对 gold 是不是太啰嗦
   - 这里还会产出一个最关键的布尔值：`task_success`
   - 当前代码里的成功判定很硬：`accuracy == 1.0` 才算成功
   - 不是“总分超过某个阈值就成功”
6. 把 `evaluation` 结果连同完整 state 一起交给 `critic`

   - 这里的 state 包括：
     - router 选了谁、各个 skill 分数多少
     - executor 实际执行了哪些工具和参数
     - gold trajectory 是什么
     - `evaluation` 的硬指标是多少
     - 当前 skill 库长什么样
     - 当前被使用的 skill 是谁
   - 所以 `critic` 不是重新算一遍硬分，而是“看着硬分和完整轨迹做诊断”
7. `critic` 总结这轮失败/成功的原因

   - 它不会直接改代码
   - 它会从 5 个维度做诊断：
     - `task_alignment`：这题整体有没有做对
     - `trigger_precision`：router 有没有选对 skill，还是根本缺 skill
     - `efficiency_and_hallucination`：执行时有没有浪费步骤、循环、乱猜参数或乱用工具
     - `progressive_disclosure`：skill 写法是不是太糊，导致 executor 不知道怎么稳定执行
     - `skill_count_pressure`：当前 skill 库是不是太多、太碎、该不该合并
   - 然后把问题翻译成“应该新建 skill / 修改 skill / 合并 skill”的建议
   - 同时给一段自然语言 reward，解释错在哪

   这 5 个维度展开看分别是在问：

   - `task_alignment`

     - 这题整体有没有做对
     - 如果没做对，最直接的失败点是什么
     - 例如：最终答案错了、最后没给选项、工具链没走完
   - `trigger_precision`

     - router 这一步到底有没有选对 skill
     - 是“明明有合适 skill 但没选中”，还是“当前 skill 库里根本缺这个 skill”
     - 这一步主要决定后面更像是 `modify_skill` 还是 `create_skill`
   - `efficiency_and_hallucination`

     - 执行过程中有没有浪费步骤、循环、乱猜参数、乱用工具、编造不存在的文件或中间结论
     - 例如：重复 `get_filelist`、调用未允许工具、参数名猜错、只做了一半就停
   - `progressive_disclosure`

     - 当前 skill 的写法是不是太空、太糊、太重，导致 executor 虽然拿到了 skill，但仍然不知道怎么稳定执行
     - 例如：skill 只写了大方向，没有把关键步骤、边界条件、默认参数、失败后的 fallback 写清楚
   - `skill_count_pressure`

     - 当前 skill 库是不是已经太多、太碎、太重叠
     - 如果多个 skill 高度重合，critic 会倾向建议 `merge_skills`
     - 如果 skill 数量还不多，这一维通常会明确说“现在没有合并压力”

   **一个关键观察可以直接记住：**

   `critic` 看到的是：

   - 当前系统做了什么
   - 标准答案应该怎么做
   - 当前库里有哪些 skill 可选
   - 这次实际用了哪个 skill
   - 硬指标结果如何

   所以它才能判断：

   - 是 router 选错了
   - 还是 skill 本身写得不够清楚
   - 还是 executor 乱跑了
   - 还是根本缺一个新 skill

   这里要特别注意：

   - `critic` 的这 5 维不是 `evaluation` 那种硬数值分
   - 它们是基于完整 state 产出的 5 维文字诊断
   - 这 5 维诊断的目的不是结算成绩，而是告诉 `actor` 下一步该怎么改 skill
8. 先检查这题是否已经成功

   - 如果 `task_success == true`：
     - 这一题直接结束
     - 不再进入 `actor`
     - 当前 iteration 会记成成功收尾
   - 如果 `task_success == false`：
     - 继续进入 `actor`
     - 让 actor 按 critic 的建议去改 skill

   这里有一个当前实现上的可优化点：

   - 真实执行顺序其实是：`evaluation -> critic -> success check -> actor(if fail)`
   - 也就是说，哪怕这题已经成功，当前实现也会先跑一遍 `critic`
   - 但成功样本随后不会进入 `actor`，所以从“失败后改 skill”的主流程看，这一步对成功样本是额外开销
   - 因此可以把它理解成一个轻度冗余：现在保留了成功样本的 `critic` 诊断日志，但这些诊断不会继续驱动 skill 修改
   - 如果以后要优化运行效率，一个直接思路是把成功判定前移成：`evaluation -> success check -> critic/actor only if fail`
   - 另一个潜在思路是加入“失败后回退”机制：因为当前一轮改完 skill 后会直接进入下一轮，同题继续尝试，但修改后的效果不一定更好；因此可以考虑解析本轮失败经验，识别这次修改是否造成退化，如果是，就引导 skill 库回退到上一版或最近稳定版本，同时把这次失败和回退原因继续追加到 `runtime_state/experience_buffer.jsonl`
9. `actor` 改 skill

   - 可能做 3 种动作：
     - `create_skill`
     - `modify_skill`
     - `merge_skills`
   - 真正落盘到 `skill_library/`
   - 同时把这次经验追加到 `runtime_state/experience_buffer.jsonl`
   - 所以 actor 做的不是“回答问题”，而是“修改未来怎么回答问题的方法”
10. 进入同一个任务的下一轮 iteration

- 下一轮会重新扫描 skill 库
- 也就是说，这个任务自己刚刚改出来的 skill，下一轮就会立刻再试一次
- 直到：
  - 任务成功；或者
  - 达到 `max_iterations_per_task`

可以把这 10 步再压缩成一句：

> `router` 决定用什么 skill，`executor` 真的去做题，`evaluation` 用硬规则结算，`critic` 根据硬结果和轨迹做诊断，`actor` 只在任务未成功时改 skill，然后同题再跑下一轮。

### 1.2 评估模式：`evaluate-tasks`

评估模式只做前半段：

1. 读任务
2. 扫 skill 库
3. `router` 选 skill
4. `executor` 执行
5. `evaluation` 打分

不会做：

- `critic`
- `actor`
- skill 修改
- experience buffer 更新

所以它的作用是：

> 拿“当前 skill 库”做一次纯验证，看现在到底能打多少分。

### 1.3 一个具体例子

如果题目是：

> 用 2019-2023 的 NDVI 和 LST 数据，计算干旱趋势并描述年度变化。

理想闭环是：

1. `router` 选中 `ndvi-lst-tvdi-annual-trend`
2. `executor` 用这个 skill 去列文件、按日期配对 NDVI/LST、生成 TVDI、算年度均值、拟合线性趋势
3. `evaluation` 发现答案对了，或者发现“虽然选对了 skill，但执行时乱用了工具/漏了最后一步”
4. 如果失败，`critic` 会指出问题，比如：
   - 选 skill 选对了
   - 但 executor 重复 `get_filelist`
   - 或者用了不允许的工具
   - 或者算出了中间结果却没给最终选项
5. `actor` 就会把这个 skill 的 `SKILL.md` 改得更明确
6. 下一轮再用改过的 skill 重跑同一题

所以这个项目的重点不是“单次把题做出来”，而是：

> 让失败的原因沉淀成 skill 改动，并在下一轮立刻验证这次改动有没有用。

## 2. 常见参数说明

下面只列最常用、最值得关心的参数。

### 2.1 所有命令都会用到的参数

| 参数         | 含义                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------- |
| `--config` | 指向配置文件，决定模型、路径、运行目录、skill 库位置等。通常用 `configs/system.local.json`。 |

### 2.2 任务选择参数

| 参数              | 用在哪                               | 含义                                                                       |
| ----------------- | ------------------------------------ | -------------------------------------------------------------------------- |
| `--task-id`     | `debug-single-task`                | 跑单题。既可以传标准化后的 `task_id`，也可以直接传原始题号，比如 `1`。 |
| `--task-ids`    | `train-tasks` / `evaluate-tasks` | 明确指定一组题，比如 `--task-ids 1 2 5`。                                |
| `--count`       | `train-tasks` / `evaluate-tasks` | 从切片后的任务列表里取前 N 个。                                            |
| `--start-index` | `train-tasks` / `evaluate-tasks` | 从数据集第几个任务开始截取，默认 `0`。                                   |

优先级：

- 如果传了 `--task-ids`，那么 `--count` 和 `--start-index` 基本就不重要了
- 如果没传 `--task-ids`，才按 `start-index -> count` 取任务

### 2.3 运行行为参数

| 参数                          | 用在哪                                  | 含义                                                                             |
| ----------------------------- | --------------------------------------- | -------------------------------------------------------------------------------- |
| `--run-name`                | 大多数运行命令                          | 指定输出目录名。强烈建议每次都写，不然就会自动生成时间戳目录，不利于对比和保存。 |
| `--reset-skill-library`     | `debug-single-task` / `train-tasks` | 运行前清空当前 skill 库。适合想从“空库”重新开始时用。危险参数。                |
| `--reset-experience-buffer` | `debug-single-task` / `train-tasks` | 运行前清空 `experience_buffer.jsonl`。适合做干净复现实验。危险参数。           |
| `--output`                  | `inspect-skills`                      | 把 skill headers 导出成一个 JSON 文件。                                          |
| `--src`                     | `convert-earth-bench`                 | 原始 benchmark `question.json` 路径。                                          |
| `--dst`                     | `convert-earth-bench`                 | 转换后的标准化数据集输出路径。                                                   |

### 2.4 `configs/system.local.json` 里最重要的参数

#### 模型配置

每个角色都有自己的一套模型参数：

- `actor`
- `critic`
- `router`
- `executor`

它们常见字段含义如下：

| 参数                | 含义                                                                                             |
| ------------------- | ------------------------------------------------------------------------------------------------ |
| `model`           | 用哪个模型                                                                                       |
| `base_url`        | 模型服务地址                                                                                     |
| `api_key`         | 访问密钥                                                                                         |
| `temperature`     | 生成随机性                                                                                       |
| `timeout_seconds` | 单次调用超时                                                                                     |
| `max_tokens`      | 主要对 `executor` 有意义；`router` 只有显式写了才会带上；`executor` 不写时默认是 `32768` |

#### 路径配置

| 参数                       | 含义                      |
| -------------------------- | ------------------------- |
| `workspace_root`         | 实验工作根目录            |
| `prompt_root`            | prompt 所在目录           |
| `run_root`               | 所有运行产物保存目录      |
| `skill_library_root`     | skill 库目录              |
| `experience_buffer_path` | 经验缓存文件              |
| `dataset_path`           | 原始 benchmark 路径       |
| `converted_dataset_path` | 转换后的训练/评估数据路径 |
| `docs_root`              | 文档目录                  |

#### 运行控制参数

| 参数                        | 含义                                                        |
| --------------------------- | ----------------------------------------------------------- |
| `skill_match_threshold`   | router 认为“这个 skill 真能用”的分数线，当前默认 `80.0` |
| `max_executor_steps`      | executor 最多能走多少步工具调用                             |
| `max_iterations_per_task` | 单个任务最多迭代多少轮“执行-评估-改 skill”                |
| `skill_count_limit`       | skill 太多时，actor 会更倾向于走 `merge_skills`           |
| `python_executable`       | skill 脚本/工具运行时用哪个 Python                          |
| `shell_program`           | 工具执行 shell 命令时用哪个 shell                           |

下面这两个参数在当前代码里定义了，但看起来还没真正用上：

- `max_router_candidates`
- `max_actor_steps`

也就是说，改它们现在大概率不会改变行为。

## 3. 常见命令

下面默认你已经在：

```powershell
cd D:\skills-evo\project_skills\project_skills
```

### 3.1 看当前 skill 库

```powershell
python -m nlrl_skills.cli --config configs/system.local.json inspect-skills
```

如果想把结果另存一份：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json inspect-skills --output runs/skill_headers_snapshot.json
```

用途：

- 看当前有哪些 skill
- 看 skill header 写得清不清楚
- 跑实验前先做快照

### 3.2 跑单题 debug

```powershell
python -m nlrl_skills.cli --config configs/system.local.json debug-single-task --task-id 1 --run-name debug_q1_local
```

从空 skill 库开始重跑：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json debug-single-task --task-id 1 --run-name debug_q1_from_scratch --reset-skill-library --reset-experience-buffer
```

用途：

- 看一题内部每轮是怎么失败/修 skill 的
- 最适合做 prompt 或 skill 行为排查

### 3.3 跑小批量训练

```powershell
python -m nlrl_skills.cli --config configs/system.local.json train-tasks --count 5 --start-index 0 --run-name train_first5_local
```

指定题号：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json train-tasks --task-ids 1 2 3 4 5 --run-name train_selected_local
```

用途：

- 让 skill 在多个任务之间逐步演化
- 看 skill 库能不能跨题积累

### 3.4 只评估，不训练

```powershell
python -m nlrl_skills.cli --config configs/system.local.json evaluate-tasks --count 5 --start-index 0 --run-name eval_first5_local
```

指定题号：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json evaluate-tasks --task-ids 1 2 3 --run-name eval_selected_local
```

用途：

- 训练完后单独验收
- 不改 skill，只看当前 skill 库的静态表现

### 3.5 转换 benchmark 数据

只有在原始 `benchmark/question.json` 需要重新转换时才用：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json convert-earth-bench --src benchmark/question.json --dst data/converted/earth_bench_skill_rl/question.json
```

## 4. 跑完后先看什么

### 4.1 先看总览

训练或单题 debug：

- `runs/<run_name>/run_summary.json`
- 单题时通常还会有 `runs/<run_name>/task_summary.json`

评估：

- `runs/<run_name>/evaluation_summary.json`

这里先回答两个问题：

1. 成功了多少题
2. 哪些题完全没跑通，为什么

### 4.2 再看具体任务

训练 run 里，一个任务通常会有：

- `task.json`
- `task_summary.json`
- `iteration_01/`
- `iteration_02/`
- ...

每轮最值得看的文件是：

| 文件                                       | 看什么                                                          |
| ------------------------------------------ | --------------------------------------------------------------- |
| `iteration_xx/skill_headers_before.json` | 这一轮开始前 skill 库长什么样                                   |
| `iteration_xx/env/state.json`            | router 选了谁，executor 实际走了哪些工具，evaluation 打了多少分 |
| `iteration_xx/critic/reward.json`        | critic 认为失败点是什么，建议 create / modify / merge 哪种动作  |
| `iteration_xx/actor/actor_decision.json` | actor 到底改了哪个 skill、写了哪些文件                          |
| `iteration_xx/skill_headers_after.json`  | 这一轮结束后 skill 库有没有真的变                               |
| `iteration_xx/iteration_summary.json`    | 本轮最精简总结                                                  |
| `iteration_xx/iteration_failure.json`    | 这一轮如果直接崩了，错误在这里                                  |

评估 run 里，一个任务最值得看的是：

- `task.json`
- `env/state.json`
- `evaluation_summary.json`
- 如果崩了，再看 `evaluation_failure.json`

## 5. 哪些结果必须保存

如果你想保证实验可复现，至少保存下面 3 类东西。

### 5.1 必存：这次 run 的目录

也就是：

```text
project_skills/runs/<run_name>/
```

这是最核心的实验记录，因为它包含：

- 配置快照
- 选了哪些题
- 每轮 skill 变化
- 每轮 router / executor / critic / actor 轨迹

### 5.2 训练实验必存：skill 库快照

训练会改 `skill_library/`，所以如果你只留 `runs/`，以后 skill 库已经变了，就不一定能复现当时状态。

最稳妥的做法是每次训练后额外保存：

```text
project_skills/skill_library/
```

或者至少保存一次对应版本的快照。

### 5.3 训练实验建议存：经验缓存

```text
project_skills/runtime_state/experience_buffer.jsonl
```

因为 actor 改 skill 时会参考历史失败经验。这个文件变了，后面的训练行为也会变。

## 6. 最小操作建议

如果你平时只想用最少命令掌握实验，建议固定这个顺序：

1. 先看当前 skill：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json inspect-skills --output runs/skill_headers_snapshot.json
```

2. 跑一题 debug：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json debug-single-task --task-id 1 --run-name debug_q1_local
```

3. 先看：

- `runs/debug_q1_local/run_summary.json`
- `runs/debug_q1_local/iteration_01/env/state.json`
- `runs/debug_q1_local/iteration_01/critic/reward.json`
- `runs/debug_q1_local/iteration_01/actor/actor_decision.json`

4. 再跑一个小批量训练：

```powershell
python -m nlrl_skills.cli --config configs/system.local.json train-tasks --count 5 --start-index 0 --run-name train_first5_local
```

```powershell
python -m nlrl_skills.cli --config configs/system.local.json evaluate-tasks --count 5 --start-index 0 --run-name eval_first5_local
```

## 7. 一句话记住这个项目

这个项目不是“写死一堆 skill 去解题”，而是：

> 用 benchmark 任务驱动 `router -> executor -> evaluation -> critic -> actor` 的闭环，让 skill 库在每个任务失败后被自动改写，并在下一轮马上验证这次改写有没有变好。
